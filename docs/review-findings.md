**Recommendation:** In the generator (plan step 2), make the latent-to-outcome and latent-to-signal links stochastic so the model has something to earn and the metrics mean something: (a) sample renewal failure as Bernoulli(sigmoid(latent)) rather than a hard threshold, so the oracle ceiling is below 1.0; (b) make each signal only partially informative with explicit benign confounders that a flat rules score gets wrong but a model can learn, e.g. ticket spikes in the first 60 days after onboarding are benign, usage dips over December are benign, and a failed Stripe payment that is retried successfully within 7 days is benign; (c) force ~15% of churners to show no observable signal and ~10% of healthy accounts to show an alarming one. Persist the per-account latent to a single eval-only table (e.g. gen_truth) that the ingest/feature pipeline never joins, and have the backtest script report three numbers side by side: oracle AUC (score = latent), model AUC, rules AUC. In plan step 4, state the expected result honestly: the model should sit between rules and oracle; if it does not beat rules, say so in the README rather than reframing.

For the event budget, decide and document before writing the generator: a product "event" is a per-account-day usage aggregate (active_users, key_actions, sessions), not a click; set an explicit per-source split of the ~200k (product-day aggregates taking the majority, then Zendesk, Stripe, Salesforce field changes, Gmail threads) with a heavy-tailed per-account count (e.g. log-normal) so the "almost nothing" accounts the VP mentions exist by construction. Ship one small gen_profile.md (or a notebook cell) with the per-account event histogram, per-source null rates, and late-arrival/duplicate rates, because "the realism of your synthetic data is part of the exercise" and the panel will ask what the realism consists of.

Add one sentence to the README's evaluation section: these metrics validate that the pipeline, point-in-time labelling, and ranking mechanics are correct on data whose generating process is known; they are not evidence about real-world churn prediction, and the first real-data step would be re-fitting and re-baselining on actual renewal outcomes.

### [reviewer-walkthrough-risk] (high) Point-in-time correctness is claimed but the two snapshot semantics it needs are not designed

**Claim:** received_at vs occurred_at is the right primitive, but the plan does not say which clock the daily snapshot uses. If features are computed by occurred_at only, late-arriving events rewrite history and training rows see information that was not known on that day (backfill leakage), which contradicts "handles out-of-order arrival honestly". The serving view needs the opposite: everything known at run time. Schema drift is listed as generator realism with no ingest counterpart. The panel will ask: "an event dated 30 days ago arrives tonight; which snapshots change, and does your training set change?"

**Recommendation:** Write one rule into the brief and README, and implement it as a single function: snapshot(account, as_of) uses only events with received_at <= as_of; feature windows (last 30/90 days) are measured by occurred_at within that set. Training rows use as_of = end of snapshot_date; the nightly job uses as_of = its fixed run timestamp, stored on every snapshot and score row (replace "snapshot date" in the traceability row with as_of; this is also what makes step 5's "idempotent and safe on rerun" true, since a rerun with the same as_of reproduces the same row). Historical snapshots are immutable. The walkthrough answer: an event dated 30 days ago that arrives tonight enters tonight's snapshot (and its 30-day window features) and no earlier snapshot, so no training row changes; the drill-down shows it on the occurred_at timeline with a "received late" marker so the CSM sees the corrected history. Add one test to step 7: insert a late event, assert all prior snapshots are unchanged and tonight's differs, and show that test in the Loom. For schema drift, keep the raw payload and a source_schema_version on the raw table, have the normaliser dispatch on it, and route rows it cannot parse to a rejects table with a reason; no parser framework, no second snapshot mode, no re-opening of historical rows.

### [reviewer-walkthrough-risk] (high) The "handled because it mattered" details are absent: missing-data semantics, entity resolution, duplicates, merges, currency, time zones

**Claim:** The plan lists messiness as something the generator will emit but names no pipeline or UI decision for it. Specific gaps the panel will probe: what a CSM sees for an account with almost no history (a confident probability from a model that has seen nothing is the wrong answer); how "zero usage" is distinguished from "this tenant has not connected product events"; how Stripe customer, Zendesk org, Gmail domain and Salesforce account are resolved into one account and what happens to orphan events; how duplicate and replayed events are deduplicated; how merged, renamed, churned and reactivated accounts are represented; how multi-currency Stripe amounts become one ARR; and what time zone a "day" boundary uses when five sources emit five timestamp formats. "Data quality checks" in step 7 names no checks and no consequence of failure.

**Recommendation:** Add a short "what the pipeline does with the mess" block (6 lines, not a decisions document) to the brief and mirror it in the README, pairing each item the generator already emits with the decision that consumes it:

1. Identity: generator emits per-source external ids (sf_account_id, stripe_customer_id, zendesk_org_id, email domain); a single crosswalk table (source, external_id, account_id) resolves them in the normalise step; unresolved rows are counted, not dropped silently, and the count appears in the nightly audit log.
2. Duplicates: dedup key (source, source_event_id) in the normalise step; the generator's duplicate injection becomes a unit test asserting the post-normalise row count.
3. Thin accounts: a minimum-evidence rule (e.g. fewer than N events or less than 30 days observed) renders "insufficient data: 3 events over 12 days" in the Monday list instead of a probability; such accounts sort to a separate section rather than mixing with scored ones.
4. Missing vs zero: NULL stays NULL into LightGBM (native handling); feature rows carry "no events in window" (0) separately from "source never seen for this account" (NULL), so the drill-down can say "no Salesforce renewal date on file" rather than showing an imputed value as a reason.
5. Time: occurred_at stored as UTC, daily snapshot keyed on UTC date. One sentence, no multi-format generator work.
6. Step 7 names its checks: duplicate rate after dedup = 0, unresolved-id rate below a threshold, null rate per feature, score distribution vs previous run; if a check trips, the nightly job writes the audit entry and does not publish new scores.

Explicitly list under "Deliberate skips": multi-currency (single currency generated), account merges/renames, and per-tenant source connectivity, so the panel sees they were considered and declined rather than missed.

### [reviewer-walkthrough-risk] (medium) Rerun safety, stale snapshots and the unattended trigger are asserted, not designed

**Claim:** "Idempotent and safe on rerun" is a claim with no mechanism: no run table, no unique key on score rows, no task dedup key, no lock against concurrent runs, no catch-up for missed days, and no definition of what the UI shows when last night's run failed. A single APScheduler worker on a free tier that sleeps idle containers will simply not fire, which breaks the "live running system" plus "runs without a human" combination. The panel will ask: "the job crashed halfway on Sunday night; what does the CSM see on Monday and what do you run to recover?"

**Recommendation:** Replace the adjective with the mechanism, in two sentences of the brief and one small table in the build. (1) Scores upsert on (tenant_id, account_id, snapshot_date, model_version), which are columns the Traceability row already stores; tasks and briefings upsert on (tenant_id, account_id, trigger_type, snapshot_date) so a rerun for the same date cannot create a second task for the CSM. (2) Make step 5's "audit log" a pipeline_run table (run_id, tenant_id, snapshot_date, status, started_at, finished_at, model_version, rows_scored) and refuse to start a run when one for the same (tenant, snapshot_date) is in_progress; with a single worker that is sufficient, no advisory lock. (3) The dashboard header reads from that table: "scores as of <snapshot_date>, last run <status> at <finished_at>", styled as a warning when status is not success or the newest success is older than one day. This is the answer to "what does the CSM see on Monday": Friday's scores with a visible stale stamp, never a blank list. (4) The job takes --date so recovery is "rerun for the missed date"; write that one paragraph in the README and list automatic backfill under deliberate skips. (5) Commit to one trigger in the brief (the worker container running APScheduler; drop "or cron") and confirm in the hosting config that the worker is not auto-stopped (on Fly a process group without services; on Railway app sleeping off). Drop the catch-up loop, the degraded-run semantics, and the GitHub Actions second trigger as scope the exercise explicitly does not reward.

### [reviewer-walkthrough-risk] (medium) The Monday list contract and the task backstop are under-specified, and "transitions" contradicts the plan's own threshold critique

**Claim:** The product is "8 accounts, in order, for reasons" but the plan does not define K, inclusion rules, what happens to an account the CSM already actioned (it will sit at the top for six weeks and train CSMs to ignore the list), or what a "transition" is after the plan argues that thresholds drift. The VP's actual ask is "nothing slips"; replacing auto-email with a queued task is right, but without task aging or escalation the system has no answer when a CSM ignores a top-ranked account. Per-CSM precision@K also requires CSM ownership in the data, which the generator list does not mention. Expect "a nightly cron job is not agentic" as a challenge.

**Recommendation:** Add three things, all small, and drop the rest of the original finding.

1. Define the trigger in the brief and in code (step 5). State it as: an account is "surfaced" when it enters its CSM's top-K by predicted 90-day renewal-failure probability, or when p rises by more than X (configurable, e.g. 0.15) over the last 7 snapshots, with a hysteresis rule so it does not flap in and out. Say explicitly that this is rank/delta based and not a colour threshold, so the brief's "thresholds drift" critique and the job's trigger do not look inconsistent on the walkthrough. K is a per-tenant config value, default 8, and the brief already flags "realistic action volume" as the business question that sets it.

2. Give tasks state and make the list honour it. Task table gets status (open, actioned, snoozed_until, dismissed with reason) written by a button in the UI. The nightly job never re-opens a task that is open or snoozed, and the Monday list shows task status and age next to each surfaced account so an actioned account does not look like a fresh alert. Put "escalation when a task goes stale (e.g. manager view after 7 days)" in the README deliberate-skips list as the honest next step for "nothing slips"; do not build it.

3. In the generator (step 2), add owner_id per account (roughly 40 CSMs across the 5 tenants, about 120 accounts each, a few accounts unassigned). Optionally add a handful of ownership-change events so point-in-time owner is a feature-pipeline concern; skip this if time is short.

Do not spend time on an "is cron agentic" defence; the exercise defines agentic as unattended, and step 5's audit log already records the decisions the job makes.

### [reviewer-walkthrough-risk] (medium) Unresolved choices and late tests make the scope hard to defend as a narrow slice built properly

**Claim:** Three "or" decisions remain open in a plan whose walkthrough is explicitly about decisions. Postgres RLS is easy to claim and hard to demonstrate correctly (session variable per request, bypass by superuser, migration complexity) and adds little over app-level scoping with an isolation test. Tests arrive at step 7 after the UI, which is where take-homes run out of time, and "how you know it works" is the grading criterion. The plan also does not say whether one model is trained across tenants or one per tenant, which the panel will ask immediately after "multiple customer organisations".

**Recommendation:** Severity: low. Drop "replace RLS", "tests are late", the milestone-1 restatement, and the schema-drift aside. Pick the three library "or"s in the brief (one line each; no further action). Record two decisions the plan currently omits, in the brief and README:

1. Model scope across tenants: one global gradient-boosting model trained on pooled daily snapshots from all 5 tenants (~1,000 accounts and too few churn positives per tenant to fit per-tenant models). State whether tenant_id is a feature; recommended excluded so that no per-account SHAP reason shown to a CSM is "your tenant". Keep "precision at top-K per CSM" as the headline metric since it is already evaluated per tenant. Note per-tenant calibration/thresholds as a deliberate skip.

2.
