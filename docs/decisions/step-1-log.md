# Step 1 log

Running log of choices made while building Step 1. Newest entries at the bottom. Design: [step-1-design.md](step-1-design.md).

## 2026-10-16 gen (tasks 1.1, 1.2): generator choices

- **Command modules receive the command name.** `app/__main__.py` calls `module.main(argv)` with `argv` equal to everything after `python -m app`, command first (`["load", "--data", "data"]`). The design says commands share modules (`load` and `ingest`, `anchors`, `train` and `score`), and a shared module cannot tell which command ran otherwise. A module that serves one command ignores `argv[0]`. The generator's own CLI also accepts argv without the command.
- **Native keys are strings in every payload.** The Zendesk `organization_id` is a digit string such as `"360000012345"`, not a JSON number, so `payload[NATIVE_KEY[source]]` compares equal to `crosswalk.external_id` without a cast. `ticket_id` stays an integer (it is never a join key).
- **Timestamps in files** use `YYYY-MM-DDTHH:MM:SSZ`. Dates in `contracts.csv` use `YYYY-MM-DD`. Both parse with `datetime.fromisoformat` and Postgres COPY.
- **History start.** A tenant's first day is `max(horizon_start, train_as_of - history_months months)`. With 36 months that is 2023-10-12 for the real configs, ten days after `horizon_start`. T5 (5 months) starts 2026-05-12, so its first renewal falls after `horizon_end` and it has no observed renewals, as PLAN.md says. Accounts start between that day and `train_as_of - 30 days`, 15% of them in the last 120 days.
- **Contracts reach `horizon_end`.** `contracts.csv` holds every cycle that starts before `horizon_end`, including renewals dated after `train_as_of` (the tail). Features read only the contract with `start_date <= as_of < end_date`, so nothing leaks, but the file does contain next-cycle ARR for renewals that have not happened yet at `train_as_of`. A renewal is decided only when its date is before `horizon_end`.
- **Outcomes.** `contracts.csv` has no outcome column (design). The outcome of each renewal (renewed, contracted, churned) is in `truth/renewal_outcomes.csv`, next to `truth/health_monthly.csv` and `truth/unobserved_factor.csv`. The pipeline learns outcomes only from the Salesforce `opportunity_stage_changed` event (and the Stripe subscription events, ignored until 3.1). Both are emitted for every renewal and agree by construction (tested).
- **CSM ownership.** About 120 accounts per CSM (the last CSM takes the remainder); `unassigned_rate: 0.01` leaves about 1% of accounts with an empty `csm_id` and an empty `owner_email`, which exercises the NULL-owner book. `tests/fixtures/tiny.yaml` sets it to 0 so ranking tests see every account owned.
- **Random streams** are `numpy.random.default_rng([seed, tenant position in the YAML, purpose])`, one stream per purpose (structure, health, renewals, one per source, lag). Changing one source's knobs does not move another source's draws. Reordering tenants in the YAML changes their data.
- **Signal model.** Latent health is AR(1): `h[t+1] = 0.92 h[t] + drift + N(0, 0.25) + shock`, shocks 1.2% per month of size 0.8 to 1.6. Churn at a renewal is `sigmoid(a + (-1.6) * health_in_the_month_before + u)` with `u ~ N(0, 1)` unobserved; `a` is solved per tenant by bisection so the mean churn probability over all possible renewals equals `base_churn`. Realised annual churn on `full.yaml`: T1 7.2%, T2 10.8%, T3 12.0%, T4 18.9% (targets 8, 12, 12, 20). Contraction is a separate draw `sigmoid(-1.9 - 1.0 h)`, ARR times 0.45 to 0.85. Mean health in the month before renewal: churned -0.87, contracted -0.50, renewed +0.04.
  - Zendesk tickets: Poisson with mean `0.125 * activity * (ARR / segment median)^0.3 * exp(-0.9 * health_seen)`. Size is the decoy: big healthy accounts file many tickets too.
  - Product: monthly rollup per live account-month, 5% dropout; active users and seat use follow `sigmoid(health_seen)`.
  - Stripe: mid-term invoices every 3 months (enterprise), 2 (mid-market) or 1 (SMB, startup); failure probability `sigmoid(-3.6 - 1.2 * health_seen)`; 70% of failures recover by retry within 6 days, the rest fail on attempts 2 and 3.
  - Gmail: Poisson, `0.29 * activity * exp(0.5 * health_seen)`; bounce share 3%, 15% when `health_seen < -1`.
  - Each source adds its own noise to health (`noise_sd` 0.3 to 0.4).
- **Lag.** `received_at = occurred_at + Exp(mean) + (with probability p) U(a, b) days`. Means: Salesforce 6h, Zendesk 4h, product 36h, Stripe 2h, Gmail 12h; late tail 2 to 5% with 1 to 10 days. About 11% of events have `received_at` after `train_as_of` (the live tail up to `horizon_end`).
- **Counts** (`full.yaml`, seed 20261016): 5,000 accounts, 43 CSMs, 194,292 events (Salesforce 16,283; Zendesk 42,997; product 78,030; Stripe 33,169; Gmail 23,813). Mix is 8.4 / 22.1 / 40.2 / 17.1 / 12.3 %, against the plan's 8 / 22 / 38 / 18 / 12. Generation takes about 5 seconds. `small.yaml`: 500 accounts, 19,498 events. Tiny: 100 accounts, 2,577 events.
- **Not in Step 1** (design section 1): identity breaks, schema drift, duplicates, `owner_changed`, planted cases, onboarding spike, thin-history flag. Account names avoid the word "health" so the truth-isolation grep (no "health" outside `truth/`) stays meaningful.
- **Byte identity** was checked across two processes with different `PYTHONHASHSEED`. Cross-OS identity (Windows against the container) is not yet checked; Step 2.14 does that. numpy's exp may differ in the last bit across CPUs, which could in principle flip a rounding.

## 2026-10-16 platform (tasks 1.3, 1.4): schema, roles, RLS and tenant_tx

- **Where things live.** `prepare_database()` is in `app/db.py` (design 2.2). `migrate()` is in `app/migrate.py`, next to its `main(argv)`, so `app/db.py` never imports Alembic. Import it as `from app.migrate import migrate`.
- **Roles are re-applied on every `migrate`.** `prepare_database` creates a missing role, then runs `ALTER ROLE ... LOGIN NOSUPERUSER ... [NO]BYPASSRLS PASSWORD <env>` every time, so the attributes cannot drift and the environment stays the source of truth for passwords. Roles are cluster-wide, so this runs under an advisory lock taken in the `postgres` maintenance database: parallel migrations of different databases on one server queue instead of failing with "tuple concurrently updated". Every local run must therefore use the same dev passwords (the `.env.example` values, which `tests/conftest.py` also sets with `setdefault`).
- **No Compose initdb script** (design 2.2). Locally, `python -m app migrate` against the Compose db creates the roles. Compose's web and worker get the role passwords from `.env` (copied from `.env.example`).
- **Nullability.** A column is NOT NULL unless the design marks it NULL, plus the columns that are empty by nature: `accounts.website_domain` (a CRM account without a website), `job_runs.error` and `job_runs.finished_at` (a running row). Each nullable column says in a comment what NULL means.
- **Constraints and indexes beyond the design.** CHECKs: `tenants.top_k > 0`, `contraction_threshold` between 0 and 1, `contracts.cycle_number >= 1`, `end_date > start_date`, `scores.probability` between 0 and 1, the four quarantine reasons. Foreign keys: `job_runs.model_version`, `scores.snapshot_id` and `scores.model_version`, `tasks.score_id` and `tasks.run_id`. Indexes for the RLS predicate and the resolve lookup: `csms(tenant_id)`, `accounts(tenant_id, website_domain)`, `contracts(tenant_id)`, `quarantine(tenant_id)`. Postgres runs foreign-key checks without RLS, so a foreign key alone does not stop a cross-tenant reference; composite keys stay skipped (PLAN.md section 10).
- **`copy_insert` errors.** Only the COPY into the temp stage goes through the psycopg cursor. The `INSERT ... SELECT` runs through SQLAlchemy, so a policy or constraint violation raises the usual `sqlalchemy.exc.DBAPIError` subclasses (`ProgrammingError` for RLS, `IntegrityError` for keys). jsonb values must be JSON text; psycopg will not COPY a dict.
- **Connections.** Every engine sets `TimeZone=UTC` and `connect_timeout=10`, so an unreachable server is an error within seconds instead of a hang (on Windows a refused connection can otherwise take minutes).
- **Test database.** `tests/conftest.py` provides the session fixture `database_url`; a DB test requests it (directly or through its own fixture). Its fallback host is 127.0.0.1 rather than the design's localhost, for the reason in `.env.example`. A test that adds tenants should delete them at teardown with the admin URL (a superuser bypasses RLS; the runtime roles cannot DELETE), as `tests/test_db.py` does, because later modules in the same session list all tenants.

## 2026-10-16 pipeline (tasks 1.5, 1.6): loader and resolve

- **Signatures.** `load_reference(data_dir, tenant=None)` and `load_all(data_dir, tenant=None)` take an optional slug or uuid, so `python -m app load --tenant t1` works; `load_all` returns `{"reference": {table: rows}, "events": {slug: rows}}`. `ResolveCounts` has a fourth field `by_reason` (quarantine reason to count) with a default, so the design's three-field form still constructs. `resolve(..., chunk_size=10_000)` and `load_events(..., batch_size=10_000)` expose the batch size for tests.
- **Empty CSV field means NULL** for every reference column (unassigned `csm_id`). The CSV timestamps and numerics go to COPY as text and Postgres parses them.
- **`load_events` skip rule.** `raw_events` has no unique key, so the only guard against loading a file twice is "tenant already has raw events: skip", under a per-tenant advisory lock inside the tenant transaction. A bad line aborts the whole tenant load with the file name and line number, and nothing is left behind.
- **`normalised_events.attrs` is the raw payload minus the identity fields** (every `NATIVE_KEY` and `EMAIL_FIELD` field name; `account_id` replaces them). So `attrs` of a product rollup holds `month, active_users, sessions, ...`, of a ticket `ticket_id, status, priority, csat`, of a Salesforce renewal `opportunity_id, stage, renewal_date, prior_arr, renewed_arr`. Feature code can read these without joining back to `raw_events`. Note this also drops `account_id` from Salesforce `account_upserted`, which is intended.
- **Matching rules.** A native key is compared as text (`str(value)`), so a numeric Zendesk id still matches. The email-domain fallback runs only for sources with an `EMAIL_FIELD` (Zendesk, Gmail), compares lower-cased domains and needs exactly one account to own the domain. Quarantine reasons, in the order they are chosen: `ambiguous_domain` (several accounts share the domain), `unknown_native_key` (a key was present but not in the crosswalk, even if the email domain was also unknown), `unknown_domain` (no key, email domain unknown), `no_identity` (neither). `quarantine.detail` holds what was tried (`native_key`, `domain`, `accounts`).
- **A quarantined event stays quarantined.** Resolve handles only events with neither a normalised nor a quarantine row, as the design says. If the crosswalk gains a row later, re-resolving those events is a Step 3 job (the quarantine table is append-only for the runtime roles anyway).
- **No `ON CONFLICT` on the resolve inserts.** A second resolver racing the first would hit the `raw_event_id` unique key and roll back loudly, which is better than silently double counting.
- **`ingest_watermark(conn, as_of)`** takes the tenant from the transaction context (row-level security), as its signature has no tenant argument. Do not call it on an `app_batch` connection, which sees every tenant.
- **Test isolation.** `tests/test_loader.py` runs the tiny config under the name `tiny-loader`, which gives its tenants ids of their own, and purges them around each test. `tests/helpers.py` also provides `purge_tenants(admin_url, ids)`, the admin-user cleanup other modules can reuse.
- **Timings, full config** (seed 20261016, local Postgres 16 in Docker): `load` of 5 tenants and 194,292 events takes about 6 s; `ingest --as-of 2026-10-12` resolves 171,843 events in about 9 s with 0 quarantined (the generator makes no identity breaks yet; Step 2.6 adds them). Gmail and part of Zendesk resolve by `email_domain`.

## 2026-10-16 ml (tasks 1.7, 1.8, 1.9): features, labels, scorer, train and score

- **Population.** An account is in a snapshot only if it has an active contract (`start_date <= as_of < end_date`, dates read as UTC midnights). On its renewal day an account already belongs to the new cycle, or is gone if it churned. `days_to_renewal` counts whole days from `as_of`'s date, so 00:00 and 23:59 on one day agree.
- **The 15 features** are the design's list. Definitions the design left open:
  - `total_event_count`: every visible non-outcome event, all history.
  - `tickets_30d` counts `ticket_created` only (an update is not a new ticket). `ticket_rate_30d_vs_prior_90d = (tickets_30d + 1) / (tickets in the 90 days before / 3 + 1)`: 1.0 means the same monthly pace as before; the +1 keeps it defined for quiet accounts.
  - Product reports are monthly and stamped on the 1st, which day windows cut badly (a 30-day window can hold zero or two of them). `active_users_last_month` is the newest report within 125 days if it is at most 45 days old; `usage_change_last_month_vs_prior_3 = last / mean(the three reports before it) - 1`. Both are NULL when the newest report is missing or stale: a missing report is unknown, not zero users. This is the one NULL beyond the design's "source not connected" rule.
  - `threads_90d` counts distinct `thread_id`. `failed_payments_90d` counts `invoice.payment_failed` events, retries included.
  - Snapshot JSON writes whole numbers as integers (a count reads 3, not 3.0) and NaN as null.
- **Outcome deny-list in one place.** `load_feature_inputs` reads outcome events too; `compute_features` drops every `OUTCOME_EVENT_TYPES` pair before computing anything, and the test feeds it all three types and checks nothing changes. `feature_spec.FEATURE_EVENTS` lists explicit event types (never an outcome type), with `EventFilter.matches(source, event_type)` for the web drill-down.
- **Anchor and nightly rows at the same `as_of` share a key.** Snapshots are unique on (tenant, account, as_of, feature_set_version), so the nightly snapshot at a Monday `train_as_of` is not written: the anchor row, computed by the same function from the same events, is the snapshot that night's scores point at. Its `kind` stays `anchor`.
- **Training reads the config's tenants only** (`tenant_id = ANY(...)`), as `app_batch`, in one transaction under an advisory lock. Label cutoff is `train_as_of`. `metrics` holds `rows`, `positives`, `positive_rate`, `censored_rows` and in-sample AUC and log loss; they are fit diagnostics, not an evaluation (Step 4). `tenant_row_counts` is keyed by tenant id. The version hashes the artifact JSON (sorted keys), so the same rows give the same version and a rerun only re-activates it. The artifact also stores `C` (1.0).
- **Scorer.** sklearn is imported inside `fit` only, so scoring from a stored artifact never loads it. A constant or all-NULL training column gets scale 1 and mean 0 or its value, so it sits at z = 0 and contributes nothing.
- **Ranking.** Ties on `rank_score` break by account id, so ranks are stable across reruns. Unassigned accounts (`csm_id` NULL) form one book (`groupby(dropna=False)`).
- **`python -m app score --as-of`** writes the nightly snapshot and scores; it does not resolve. Run `ingest --as-of` first, or use `nightly`, which does all three.
- **Test isolation.** `tenants.slug` is unique, so the tiny tenants and `tiny-loader`'s cannot coexist. Each ML test module purges its seeded tenants at teardown (`purge_tenants`); `model_versions` rows stay, and the next `seed_tiny` re-activates the same version.
- **Timings, full config** (local Postgres 16, after `load` and `ingest --as-of 2026-10-12`): `anchors` writes 316,410 anchor snapshots in about 100 s (147 Mondays from 2023-12-25; pandas groupby on UUID objects dominates, kept for simplicity). `train` labels 204,567 anchors (111,843 censored), 18.6% positive, in-sample AUC 0.63, in 18 s. `score --as-of 2026-10-13` writes 4,573 snapshots and scores in 5 s. A rerun of `anchors` recomputes everything and writes 0 rows; stored anchors were re-checked against a fresh `compute_features` (16,960 rows, 0 mismatches).

## 2026-10-16 jobs (tasks 1.10, 1.11, 1.13): nightly job, worker, bootstrap

- **Three transactions per tenant**, as designed: claim, work, finish. `run_id` is `stable_uuid("run", "nightly", tenant_id, run_date)`, so a re-claimed night keeps its id and the score rows that point at it. Re-claiming resets `as_of`, `trigger`, `started_at`, `counts`, `stage_ms`, `error` and `finished_at`. Only a `failed` or `running` row is re-claimed; a `succeeded` row makes the claim return nothing and the tenant's result is `no_op`, with no row written or changed. Any later `as_of` on the same UTC date is the same night, so it is a `no_op` too.
- **A failed night** records `status='failed'`, the exception as one line in `error` (type and message, capped at 2,000 characters; the traceback goes to the log), empty `counts` and NULL `model_version`, because the work transaction rolled back and nothing it counted was kept. `stage_ms` keeps the stages that finished, so the first missing stage is the one that failed.
- **Counts are new rows.** `counts = {events_normalised, events_quarantined, snapshots_written, accounts_scored}`. On a Monday `as_of` the anchor row already holds the snapshot key (ml entry above), so the bootstrap night shows `snapshots_written = 0` and `accounts_scored` equal to the active accounts. If `python -m app score` already scored a night by hand, `nightly` for that night writes 0 scores; use `nightly`, not `score`, for real nights.
- **The active model is looked up first** inside the work transaction, so a night with no model fails before ten seconds of resolving.
- **A `running` row is re-claimed at once.** Two runs of the same night at the same moment (a CLI run during a scheduled one) would both execute. Every write is keyed, so nothing doubles, but `job_runs` keeps the later result. The worker's `max_instances=1` prevents this for scheduled runs; stale-run detection and per-tenant advisory locks are Step 5.
- **Scheduled `as_of`.** APScheduler 3 does not hand the job its scheduled fire time, so `as_of` is `now_utc()` truncated to the minute, as the design says. `misfire_grace_time` is 3,600 s rather than the default 1 s: a fire that starts late (busy host, paused VM) still runs instead of being skipped silently. `coalesce=True` folds a backlog into one run.
- **Worker process.** A SIGTERM handler turns `docker stop` into a normal exit (Python as PID 1 ignores SIGTERM otherwise). Log timestamps are UTC. A bad `NIGHTLY_CRON` fails at start, not at 2 a.m. The worker reads `BOOTSTRAP_CONFIG` and `DATA_DIR`, defaulting to `config/full.yaml` and `data`.
- **Bootstrap** prints each step's time. Step 3 (refuse tenants the config does not name) runs after `generate`, because generating is cheap and reads nothing from the database. A second bootstrap still recomputes the anchor features before writing 0 rows (about 70 s on full); the worker only bootstraps when `model_versions` is empty, so this matters only for a manual rerun.
- **Compose.** The shared `x-app` block passes `BOOTSTRAP_CONFIG`, `NIGHTLY_CRON`, `CLOCK_OVERRIDE` and `PORT`, interpolated from `.env` with defaults, and fixes `DATA_DIR=/srv/data`. Secrets still come only from `.env`. The worker has `restart: unless-stopped`, so a crash or a half-finished first bootstrap is retried, and every step is idempotent. There is no data volume: generated data is only needed while bootstrapping, and regenerating takes about 6 s.
- **Test isolation.** `tests/test_bootstrap.py` runs before `tests/test_db.py`, which expects `model_versions` to be empty. Its teardown therefore deletes, as the admin user, the model rows it created, after purging its tenants.
- **Timings** (local Postgres 16): bootstrap of `full.yaml` into an empty database takes 117 s: generate 6.3, load 5.6, resolve 8.6, anchors 70.1, train 17.6, first night 5.5 (5,000 accounts, 194,292 events, 316,410 anchors, `logreg-bc14777dd25e`). The next night (`nightly --as-of 2026-10-13T02:00Z`) takes 11.7 s for 5 tenants and 4,573 accounts. The largest tenant, t1, takes ingest 0.3 s, snapshot 2.1 s and score 0.4 s. `small.yaml` bootstraps in 18 s. The worker ran end to end with `CLOCK_OVERRIDE=2026-10-14T02:00Z` and `NIGHTLY_CRON="* * * * *"`: it bootstrapped first, then the first fire succeeded for both tenants and the next fire was a `no_op`.
